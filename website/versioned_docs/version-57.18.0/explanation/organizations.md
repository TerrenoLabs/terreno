# How organization tenancy works

Terreno treats organizations as an optional framework primitive. Existing
single-tenant apps do not pay a migration or authorization cost; multi-tenant
apps opt in at the access, application, model, and admin layers. New apps
generated by `create-terreno-app` opt in by default.

## Identity and authorization layers

Platform and tenant authority are separate:

| Authority | Storage | Scope |
| --- | --- | --- |
| `superadmin` | `User.roles` | Every framework permission |
| `operator` | `User.roles` | Organization directory and every organization |
| `org-admin` | `Membership.roleName` | One organization |
| `member` | `Membership.roleName` | One organization; app permissions decide actions |

`user.admin` does not imply operator access. `org-admin` is deliberately not a
global RBAC role: putting it on `User.roles` grants nothing. During an
organization request, `createAccess({organizations: true})` adds the current
active Membership grants to the normal role permissions.

## Request context

Tenant routes resolve `X-Organization-Id` after authentication. An operator or
superadmin may enter any organization but must choose one. An org-admin with
exactly one administered organization may omit the header; Terreno infers it.
Ambiguous or unauthorized context fails before model queries run.

The resolved organization and membership are stored in AsyncLocalStorage as
well as `req.organization` / `req.membership`. This lets `OrgQueryFilter` add
the server-owned organization id without trusting a client query parameter.

## Isolation boundaries

Tenant isolation uses multiple checks rather than one convention:

1. `orgContextMiddleware({required: true})` rejects missing or unauthorized context.
2. `OrgQueryFilter` ANDs the selected organization into list and search queries.
3. `Permissions.IsOrganizationMember` rejects cross-org object reads and writes.
4. Create hooks overwrite client-supplied organization ids.
5. `orgScopedPlugin` rejects any post-create change to `organizationId` (REST, admin, sync, direct save).
6. Sync scopes resolve active Membership rows and partition streams by organization.

`AdminApp({organizations: true})` applies these boundaries automatically to
admin models whose schema contains `organizationId`. Models without that path
remain platform-scoped.

## Disabled organizations

When `Organization.disabled` is `true`, tenant context and membership mutations
stop, but operators can still manage the organization record itself:

| Surface | Disabled org behavior |
| --- | --- |
| `orgContextMiddleware` / inferred org context | 403 `Organization is disabled` |
| `GET /orgs/mine` | Disabled orgs omitted from the switcher list |
| `GET /orgs` (operator directory) | Disabled orgs still listed |
| `GET` / `PATCH /orgs/:id` | Allowed (operators use `PATCH` with `disabled: false` to re-enable) |
| `POST` / `PATCH` / `DELETE /orgs/:id/members` | 403 while disabled |
| Soft-deleted orgs | Still 404 everywhere |

Disabling or deleting an organization suspends its memberships. Re-enabling does
not automatically reactivate them.

## Why organizations are optional

Automatically registering routes, roles, or Mongoose models would change
existing apps merely because they upgraded `@terreno/api`. Instead:

- `createAccess` omits Membership grants and the `operator` seed unless
  `organizations: true`;
- `TerrenoApp` does not mount `/orgs` unless organizations are enabled;
- `AdminApp` does not scope models unless organizations are enabled;
- Organization and Membership Mongoose models register lazily on first use.
  Apps add fields to `Organization.settings` with `createOrganizationSettingsSchema`
  and `registerOrganizationSettings`, not by replacing the Organization model.

This keeps upgrades backward compatible while letting bootstrap generate
multi-tenant-ready apps.
