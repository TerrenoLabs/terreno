# Upgrading to 57.15.0

**Action required:** No
**Affected packages:** @terreno/api, @terreno/syncdb

## Summary

SyncDB pages every stream through one `POST /sync/snapshot/batch` request per round instead of
one `GET /sync/snapshot` per stream. With many synced collections, cold start is faster and a
reconnect with no changes costs 2 requests (`GET /sync/streams` plus one batch) whatever the
collection count. The web IndexedDB persister now serializes the store once per write instead of
once per transaction, so bootstrap no longer leaves a long save backlog.

## Breaking changes

None

## Deprecations

None

## New capabilities

### `POST /sync/snapshot/batch`

`SyncApp` mounts the route automatically. The body is
`{streams: [{stream, cursor?, legacyCursor?}], limit?}`, with at most 500 streams.
`limit` is the row budget for the whole response (default 5,000, max 10,000). The response is
`{pages}`, one `GET /sync/snapshot`-shaped page per stream. `GET /sync/snapshot` is unchanged.

Upgrade `@terreno/api` and `@terreno/syncdb` together for the speedup. A 57.15.0 client talking
to an older server sees a 404 from the batch route and falls back to per-stream paging
(`snapshotConcurrency` streams at a time). An older client keeps using `GET /sync/snapshot`.

### `snapshotConcurrency` scope

`createSyncDb({snapshotConcurrency})` now applies only to per-stream paging: `forceResync()` and
the fallback against servers without the batch route.

## Verification

- `bun run compile` and `bun run lint` at the app root
- After deploying the backend, open the web app with dev tools and confirm a reconnect sends one
  `POST /sync/snapshot/batch` instead of one `GET /sync/snapshot` per collection
